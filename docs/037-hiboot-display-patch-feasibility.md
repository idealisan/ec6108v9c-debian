## 1. Q1 — 显示函数体到底在不在（换方法重查）

### 1.1 本次换用的方法（相对 `docs/031 §3.2` 的 7 种「字符串交叉引用」）

`docs/031` 找的是「字符串被谁引用」；本次改为**找函数本身**：

1. **ARM 函数序言扫描**：全文件 capstone `skipdata=True` 反汇编，收集
   `push {..., lr}` / `stmdb sp!, {...lr}` / `mov ip, sp` 三类序言，得候选函数入口表。
2. **`bl` 调用图**：逐条解出 `bl` 目标，统计被调用者分布。
3. **函数名串相邻排布**：把 23 个显示相关串按 VA 聚成簇，检查簇内 / 簇 ±4KB 是否有序言。
4. **字面量 / ADR 范围交叉引用**：不只查「精确串 VA」，也查 `ldr[pc]` 字面量与
   `add/sub pc,#imm`（ADR）是否落在**整个簇区间**内。
5. **簇附近的代码指针表**：搜索 ≥6 个连续、值落在代码区（`0x00C00000–0x00C90000`）的 word，
   判断是否存在「函数名串 ↔ 函数地址」配对表。
6. **SDK 源码对照**：`TMP/sdk-src/` 的 `hi_gfx_show.c` / `hi_gfx_layer.c` 给出真实 ABI 签名。

覆盖量（全文件，capstone `skipdata=True`）：

| 对象 | 指令数 | 序言候选 | `bl` 目标 | ADR/`add pc` 命中 |
|---|---|---|---|---|
| 原厂 1 MB | 262,144 | 1,359 | 1,390 | 578 |
| 社区顶层 | 134,816 | 1,078 | 1,228 | 4,169 |
| 社区 `mv100` | 134,818 | 1,078 | 1,228 | 4,169 |
| `burn` | 129,867 | 1,085 | 1,215 | 3,528 |

[观察] 序言密度按 64 KiB 桶：原厂 0–7 号桶（VA `0x00C00000–0x00C80000`）每桶 103–211 个；
8 号桶起骤降至 0–29 → **代码区约 `0x00C00000–0x00C80000`**，其后为 rodata/data。

[观察] 显示串簇内容示例（社区 `mv100` 簇 1，`0x6933c` 起）：
`PRODUCT_DisplayInit` / `GetDispParam` / `Logo_Main` / `HI_ADP_DispInit` / `HI_LogOut` —— 是一组

同样 0 个字面量引用。

### 1.3 一个必须排除的假阳性（范围扫描的代价）

[观察] 范围扫描在社区两份里得到 **18 条 `ldr[pc]` 落在簇内**，全部指向 `0xc69388`。
回读该 VA：`\x08\x08\x08…(((((\x08…` —— 是 **ctype / 字符分类位表**，不是显示字符串。
radare2 核对引用点（如 `0xc14aec`、`0xc14e48`、`0xc1603c`、`0xc5b7c4`）：均为
`ldrb r3,[r1,r3]; tst r3,#3` 一类**通用字符串解析 / `strtoul` 字符分类代码**。
→ **[观察/排除]** 这 18 条不构成显示函数体证据；精确命中数仍为 0（`docs/033 §2` 第 3 条
「不靠指令外观推断行为」生效）。

### 1.4 判定与负面边界

[观察] **在「全文件 capstone `skipdata=True` 反汇编 + 全部序言 + 全部 `ldr[pc]` 字面量 +
全部 ADR/`add pc` + 全部 `bl` 目标 + 簇附近代码指针表 + radare2 关键片段互验**
范围内，4 份 hiboot **未定位到任何显示初始化函数体**，也没有可给出的候选地址区间。
显示相关字符串是**孤立 rodata**（函数名表 / 调试串保留，函数体不在这些镜像中）。

[推断] 可能原因（不证实）：显示库被条件编译剔除、函数体在另一阶段 / 另一分区镜像里、
或这些串来自 SDK 全量构建的 `__func__` / 日志模块名表。
[未知] 不能就此断言「硬件上不存在显示初始化」——与 `docs/031 §3.4` 一致，保留存疑边界：
**「这批镜像里没有可定位的显示入口」≠「设备没有显示能力」**；正常开机能画 p5 logo
（`docs/036 §0`）说明能力客观存在，只是路径 / 二进制尚未定位。

→ 对 `docs/036 §6.3` 门槛 1 的判定：**FAIL**（未定位到函数体）。

## 2. Q2 — `go` 命令可用性（零补丁路径优先评估）

### 2.1 `do_go` 反汇编实证（4 份镜像，radare2 + capstone 逐条一致）

`cmd_tbl_s`（28 B 步长）里 `go` 记录与实现：

| 对象 | `go` 记录文件偏移 | `cmd` 函数 VA |
|---|---|---|
| 原厂 1 MB | `0x93a2c` | `0x00C17904` |
| 社区顶层 | `0x80208` | `0x00C0C740` |
| 社区 `mv100` | `0x80210` | `0x00C0C740` |
| `burn` | `0x7b5e4` | `0x00C0CD54` |

[观察] `go` 记录（`mv100`，radare2 `px` 确认）：
`name=0xc77f8c("go")`、`maxargs=0x10`、`repeatable=1`、`cmd=0x00c0c740`、
`usage=0xc77f8f`（`start application at address 'addr'`）、`help=0xc77fb3`（`addr [arg ...]`）。

[观察] `do_go` 实现（社区 `mv100` @`0x00C0C740`，原厂同构 @`0x00C17904`，radare2 + capstone 互验）：

```asm
0x00c0c740  cmp   r2, 1                 ; argc 检查
0x00c0c744  push  {r4, r5, r6, lr}
0x00c0c748  bgt   0xc0c75c             ; argc>1 才继续，否则打印 usage 返回
0x00c0c75c  mov   r4, r3               ; argv
0x00c0c764  mov   r1, 0
0x00c0c768  mov   r2, 0x10             ; base 16
0x00c0c76c  ldr   r0, [r4, 4]!         ; argv[1]
0x00c0c770  bl    0xc5d0d4             ; simple_strtoul(argv[1],NULL,16)
0x00c0c778  mov   r5, r0               ; r5 = 目标地址
0x00c0c77c  ldr   r0, [..]            ; "## Starting application at 0x%08lX ...."
0x00c0c780  bl    0xc12c90             ; printf
0x00c0c784  mcr   p15, 0, r0, c7, c5, 0   ; ICIALLU：作废 I-Cache
0x00c0c788  mcr   p15, 0, r0, c7, c10, 4  ; DSB：数据同步屏障
0x00c0c78c  mov   r2, r4
0x00c0c790  sub   r1, r6, 1           ; argc-1
0x00c0c794  mov   r0, r5               ; 目标地址
0x00c0c798  bl    0xc0c730             ; 跳板
0x00c0c79c  adds  r4, r0, 0
0x00c0c7a4  ldr   r0, [..]            ; "## Application terminated, rc = 0x%lX."
0x00c0c7ac  bl    0xc12c90             ; printf
0x00c0c7b0  ... pop {r4,r5,r6,pc}     ; 返回 hush / bootcmd 继续
```

[观察] 跳板 `0x00C0C730`（原厂 `0x00C178EC`）：

```asm
0x00c0c730  mov   r3, r0             ; r3 = 目标地址
0x00c0c734  mov   r0, r1            ; r0 = argc-1
0x00c0c738  mov   r1, r2            ; r1 = &argv[1]
0x00c0c73c  bx    r3                ; 原厂为 blx r3 → 目标作为函数被调用
```

→ **[观察]** `go <addr>` 把目标当作 `int fn(int argc, char **argv)` 调用；
**不关 MMU、不关 D-Cache（仅 ICIALLU + DSB）、不关中断**（回答 `docs/004 §6` 的未验证项）。
[观察] 目标若正常 `bx lr` / `pop {...,pc}` 返回，控制回到 `do_go` → 打印
`## Application terminated` → 返回 hush → **`bootcmd` 后续命令继续执行**（不是一去不回）。

### 2.2 「用 `go` 触发显示」的硬前提清单

1. **[未知/FAIL]** 需要一个**已知 VA、可调用**的显示初始化函数体 —— Q1 已证 4 份镜像里定位不到。
2. **[观察]** ABI 不匹配：`go` 只给 `r0=argc-1`、`r1=argv`；而 SDK 实证签名是
   `HI_GFX_ShowLogo(HI_BASE_GFX_LOGO_INFO *)`、`BOOT_GFX_DisplayLogoWithLayer(info, LayerId, DecSurface)`
   （`TMP/sdk-src/hi_gfx_show.c:73`、`hi_gfx_layer.c:102/251`）。把 `argc-1` 当结构体指针 →
   [推断] 解引用非法地址，大概率崩溃 / 挂死，链中断。
   `TMP/sdk-src/` 内**未检索到** `PRODUCT_DisplayInit` / `Logo_Main` 的定义（无「无参入口」可用）。
3. **[未知]** 目标返回后是否破坏 U-Boot 全局状态（gd / env / 栈）未验证。
4. **[观察]** `cmd_display.c` 是 U-Boot **点阵数码管** `display` 命令（`DISP_SIZE 8`、
   `CWORD_CLEAR 0x80`），**不是 HDMI**；不能拿它当显示入口（`docs/036` 已提醒）。
5. **[观察]** 命令表里没有显示命令；`docs/035` 的完整可达显示链在 **recovery 内核**
   （VA `0xC0xxxxx`），与 hiboot 的 `0x00Cxxxxx` 不是同一地址空间，**地址不能照搬**。

### 2.3 判定

[观察] **`go` 命令本身可用**（`do_go` 可达、返回后链继续、仅需作废 I-Cache + DSB）。
[推断] **但「用 `go` 在 `bootcmd` 里触发显示」= 否**：缺可调用函数 VA、ABI 不匹配、
目标行为未验证。把 `go <任意地址>` 放进链里反而引入「跳飞」风险（地址未知时更危险）。
→ 对 `docs/036 §6.3` 门槛 2 的判定：**FAIL**（零补丁路径关闭）。

## 3. Q3 — 最小二进制补丁 / CRC / 头 / 回滚镜像

### 3.1 补丁点（若载荷存在，理论插入位置）

[观察] 刷机分支入口可定位：社区 `mv100` 的 U 盘 `bootargs.bin` 串 VA `0xc77e90`
被 `0xc0c2a4` / `0xc0c2cc` 两处 `ldr r0,[pc,#imm]` 引用（字面量池 `@0xc0c338`），
其所在函数 `0x00C0C29C` 的完整流程 = USB 探测 → FAT 查找 → `fatload` 到 `0x1000000`
→ 复制 64 KiB → `env` 处理 → **CRC32 校验（`0xc0c30c`）→ 置「U 盘 env 有效」标志
（`0xc0c324 streq r5,[r3,#0x14]`）**（与 `docs/036 §4.1` 对社区顶层的实证同构）。

[观察] 两个候选机械落点：

| 落点 | 文件偏移 | 改动 | 字节数 |
|---|---|---|---|
| A. 劫持 `go` 命令 | `mv100` `go` 记录 `@0x80210`，`cmd` 字段 `@0x8021C` | 改写 4 字节指针指向放入 cave 的载荷 | 4 B 指针 + 载荷（大小 [未知]） |
| B. 在 env 分支插入 `bl` | `0xc0c324` 附近 | 覆盖 1 条指令为 `bl <trampoline>`，trampoline 放 cave | 4–12 B trampoline + 载荷（大小 [未知]） |

[观察] **代码洞（code cave）**：`mv100` 在 `0x4000` 之后只有 9 段 ≥64 B 的零填充，
最大 **255 B**；原厂 1 MB 镜像有 430,135 B 的大洞（文件 `0x92f09`），但那是**原厂 p1**，不是补丁目标
`mv100`。[推断] 255 B 容不下完整显示初始化载荷；且 `0x18ae` 一带的零填充位于
**BootROM 消费的 DDR 参数区（`0xe0–0x200`）附近，写它会破坏 DDR 训练**。

### 3.2 头结构 / CRC / `verify=n`（明确结论）

[观察] 4 份镜像头 `0x00–0x60` 同构：
- `0x00` 复位向量 `ea000819`；`0x04–0x1c` 7 × `e59ff014`；`0x20–0x3b` 异常向量跳转表
  （`0x00C04C40` 等值）；`0x3d` 起 `YZC`（`0x3c` 为 `0x0d`）；`0x40` 起 `v1.1.0`。
- `0x50 = 0xA0`、`0x54 = 0x18A0`（社区 / burn）/ `0x18E0`（原厂）—— [推断] 疑似
  DDR 参数 / 区域长度字段，格式未完全逆向（`docs/004 §6`）。
- `0xe0–0x200` 是 DDR 训练寄存器 / 值对（`0xf8a220c8` 等），**由 BootROM 消费**。

[观察] **CRC 检索**：对 `mv100` 计算 `crc32(whole)`、`crc32(0x200..end)`、`crc32(0x0..0x200)`、
`crc32(0x0..0x40)`、`crc32(0x40..0x200)`，**在头 `0x0–0x100` 的 word 里未检索到任何匹配项**。
[观察] 4 份镜像尾部均为 rodata + 零填充，`mv100`/顶层/`burn` 尾部出现同一常数 `0x00000008`；
[推断] 是数据 / 对齐残留，**未检索到全镜像 CRC/签名字段**。

[观察] **`verify=n` 在 4 份 hiboot 二进制里 0 命中**（它是 U-Boot **env 变量**，存在于
`bootargs.bin` / p2 环境里，`docs/005 §5`、`docs/025 §5.5.1`）。
→ **[推断]** `verify=n` 控制的是 `bootm` 对**内核镜像**的签名校验，**与 BootROM 对 p1 的校验是两回事**；
不能拿 `verify=n` 推断「补丁 p1 无需重算头 / CRC」。

[推断] 一个旁证：社区包 `flashfastboot` 把 `mv100/fastboot.bin` 写进 p1 且开机成功
（`docs/036 §6.2`、`docs/016`）；社区顶层与 `mv100` 的**前 `0x4000` 字节完全相同**，但
`community_top` 与原厂 1 MB 差异达 493,224 B（遍布 `0x20–0x83a7f`，每个 4 KiB 桶约 4000/4096 B 不同），
**两份都能引导** → [推断] BootROM 不大可能要求「某份构建专属的全镜像校验和」。
[存疑] 但 `docs/004 §6` 明确「YZC 私有头格式未完全逆向」，BootROM 是否校验
私有头 / DDR 参数区之外的字段，**未证实**。

> **明确结论（门槛 3 的 CRC 部分）**：在本文检查范围内**未检索到**需重算的头 CRC 字段；
> 但「补丁后 CRC/头是否需要重算」**不能给「明确不需要」** —— 标 **[存疑]**。

### 3.3 补丁字节数与偏移（诚实边界）

[未知] **无法给出补丁字节序列 / 具体偏移**：最小机械改动是 4 字节（`go` 记录的 `cmd` 字段
`@0x8021C`）或 4–12 字节 trampoline（`@0xc0c324` 附近），但**显示初始化载荷本身不存在**
（Q1），其字节数、内容、偏移都无从谈起；按 `docs/033 §2` 第 3 条，**不编造载荷 / 偏移 / 字节**。
[观察] 可给出的只有：社区顶层与 `mv100` 首差异 `@0x2054`；差异遍布 `0x2054–0x83a7c`，
**代码区 `0x0–0x40000` 约 99% 相同**（`0x20000–0x21000` 全同，`0x10000` 桶 4044/4096 同），
差异集中在 `0x49000–0x5A000` 与 `0x76000–0x83000`（rodata/串/数据）。
→ [推断] 若补丁落在代码区，对顶层与 `mv100` 同样适用；但 `go` 记录偏移不同
（顶层 `0x80208`、`mv100` `0x80210`），**不能跨镜像照抄偏移**。

### 3.4 回滚镜像评估

| 候选 | 是否已知可引导 | 依据 / 限制 |
|---|---|---|
| `mv100/fastboot.bin`（`3bded87f…`） | **是（唯一实测）** | 社区包 `flashfastboot` 把它写进 p1、用户成功刷机（`docs/036 §6.2`、`docs/016`） |
| 顶层 `fastboot.bin`（`fd5b4ac6…`） | [推断] 可能 | 与 `mv100` 前 `0x4000` 相同、YZC 头合法；但**未被 flash 流程写入 p1**，未证实 |
| `backup_stock/fastboot.img`（`bac0be9f…`，原厂 1 MB） | [推断] 可能 | 出厂 p1 备份；但走 Android_Main 正常路径，U 盘 env 行为未确认（`docs/013 §1`） |
| `fastboot-burn.bin`（`d5bb8272…`） | [未知] | CI 早期产物，角色 / 可引导性未确认 |

[存疑] **关键限制**：以上任何一份作为「回滚源」，**投递通道都依赖 p1 本身**——
`flashfastboot` / 读 U 盘 `bootargs.bin` / `mmc write` 全在 p1 hiboot 里跑。p1 写坏 →
这些命令不可达 → 回滚源**无法自动写回**（`docs/006 §5` 场景 C 需串口 + HiTool，本机无）。
→ 对 `docs/036 §6.3` 门槛 3 的判定：**不完整 / 存疑**（有镜像，无可靠投递）。

## 4. Q4 — 风险清单与 go/no-go 建议

### 4.1 「写 p1 后短接兜底是否仍有效」

两份既有文档给出**冲突模型**，本文不替用户二选一，逐条陈列：

- **模型 A（`docs/036 §1`、`docs/013 §1`、`docs/004 §2.1`）**：短接上电 → BootROM 从
  **eMMC LBA0 加载 p1** 到 `0x00C00000` → p1 hiboot 读 U 盘 `bootargs.bin` → 跑 `bootcmd`。
  [推断] 若成立，**p1 写坏 → 第 1 步就失败 → 短接 + U 盘兜底同时失效**。
- **模型 B（`docs/025 §5.5.2`，histb 官方文档）**：USB_BOOT 短接时 BootROM 可从
  **U 盘 FAT32 根目录加载 `fastboot.bin` 到 RAM 执行（不写 flash）**。
  [推断] 若成立，U 盘根放一份已知可引导 `fastboot.bin` 可**绕过**写坏的 p1 → 兜底有效。
- [观察] `docs/001 §7.2` 明确「hiboot 如何触发 U 盘 `bootargs.bin` 执行（按键组合 /
  自动检测）**尚未从二进制完全确认**」；`docs/004 §6`「YZC 头未完全逆向」。
  `docs/036 §4.1` 已实证 **p1 hiboot 内**的 `bootargs.bin` 加载路径，但未证明 BootROM 的取码来源。

> **[存疑] 结论**：写 p1 后短接兜底**是否仍有效，证据冲突、未定**。
> 按 `docs/006 §5` 场景 C，模型 A 成立且 p1 损坏时只能串口 HiTool；本机无串口硬件 →
> **按最坏情况应判「否 / 不可逆」**。这一条本身就是 go/no-go 的否决项。

### 4.2 风险清单

| # | 风险 | 级别 |
|---|---|---|
| 1 | Q1 未定位到显示函数体 → 无载荷可打 | [观察] 确定 |
| 2 | Q2 `go` 零补丁路径关闭（ABI 不匹配、地址未知） | [观察]+[推断] 确定 |
| 3 | YZC 私有头未完全逆向；是否需重算头/CRC [存疑] | [存疑] |
| 4 | `verify=n` 是 env 级，不覆盖 BootROM；「签名关闭」不能当 p1 安全网 | [观察] 确定 |
| 5 | 写 p1 破坏短接兜底本身（模型 A）→ 无串口 / HiTool 不可逆 | [存疑] 最坏=否 |
| 6 | 无 ARM 交叉工具链、无法重编译 hiboot；只能二进制补丁 | [观察] 确定（`docs/036 §6.2`） |
| 7 | `mv100` 代码洞最大仅 255 B（且部分在 BootROM DDR 参数区附近），载荷放不下 | [观察] |
| 8 | 顶层 / `mv100` 偏移不同（`go` 记录 `0x80208` vs `0x80210`），跨镜像照抄会打错位置 | [观察] |
| 9 | `bootcmd` 的「;` 链 + 每轮 reset 后 U 盘 env 重导入（`docs/036 §4.1`）→ 分阶段状态机不成立 | [观察] 确定 |

### 4.3 go/no-go 建议：**NO-GO（不写 p1）**

对照 `docs/036 §6.3` 五条门槛：

| 门槛 | 判定 |
|---|---|
| 1 先定位显示初始化函数体 | **FAIL**（Q1，[未知]） |
| 2 优先评估 `go` 零补丁路径 | **FAIL**（Q2，ABI / 地址双缺） |
| 3 补丁 CRC/头/回滚镜像明确 | **存疑 / 不完整**（§3.2–3.4） |
| 4 先在 Live-USB 零写入环境验证 | **未做**（无载荷可验） |
| 5 任一条不满足 → 不写 p1，退回零风险分级 logo | **触发** |

[推断] 即使强行补丁，收益也存疑：`docs/036 §4.2` 已证「U 盘刷机分支不做显示初始化」，
但**显示能力是否存在于 p1 二进制仍 [未知]**（Q1）；在无载荷、无可观测手段（无串口、
console 只有 `serial`）的前提下，任何 p1 写入都是**不可逆且结果不可验证**的盲改。

**建议**：维持 `docs/036 §4.2` 的零风险最小改造（每步写一张合法 stage logo 到 p5，
用 `;` + `if`，不用 `&&`，不碰 p1、不增加 `reset`），把「授权改 p1」保留为
**待 Q1 有实质突破（定位到显示函数体）后再重启的决策，且必须先解决兜底模型 A/B 的存疑**。

### 4.4 若将来重启，最小验证步骤（顺序不可颠倒）

1. **[观察] 先厘清兜底模型**：在 Live-USB（零写入）环境用一份已知可引导
   `fastboot.bin` 放 U 盘根 + 短接上电，验证 BootROM 究竟走模型 A 还是 B
   （`docs/013 §2` 方案 A、`docs/025 §5.5.2`）。**此步不写任何 eMMC**。
2. **[观察] 验证 `go` 返回语义**：`bootcmd` 里 `go <一个已知无害函数 VA>` 后接一个
   可观测的 `mmc write` 标记，确认链继续、`## Application terminated` 路径成立（本文 §2.1 已静态实证，
   此步是真机确认）。
3. **[未知] 先取得显示函数体 VA**：需另一份含显示代码的二进制 / 完整 SDK 可编译产物；
   在此之前**不进入补丁设计**。
4. **[推断] 之后才在 Live-USB 零写入环境验证补丁镜像**（`go` / `bootcmd` 级行为），
   再考虑写真机 p1；写真机前必须备好 §3.4 的 `mv100` 回滚镜像 + 确认兜底通道有效。
5. 任一步失败 → 停在零风险分级 logo 方案。

> 2026-11-08。分支 `main`。回应用户的根本质疑：**「刷机/引导程序究竟是如何绘制图像的」到现在没搞清楚，

>
> 承接：`docs/031/037`（社区 4 份 hiboot 显示字符串「孤立 rodata、0 代码引用」负结果）、
> `docs/040`（真机写 fb0 能显示）、用户确认 p7 logo 图是原厂开机早期画面。

## 0. 诚实结论先行

> **[观察] p1 的代码区确实存在**（`0x00000–0x7FFFF`，1313 个 ARM `push {...,lr}` 函数序言），
> **数据/符号名池在 `0x80000+`**（ASCII 100%）。显示相关名字（`PRODUCT_DisplayInit`/`HDMI_Display`/
> `HI_GFX_ShowLogo`/`PDM_ReadLogoData`/`HI_DRV_PDM_AllocReserveMem`/`boot logo show!!!`/`LOGO_TABLE`）
> 全落在 `0x79000+` 的**字符串区**，是文本不是代码。
>
> **[观察] 用本轮方法（代码区 ARM/Thumb-2 `ldr [pc,#imm]` 字面量扫描），代码区对这些符号名 0 引用**。
> 与 `docs/031/037` 的负结果一致，但**不等于**「显示代码不在 p1」——见 §3 的边界。
>
> **[未知·核心缺口] 引导程序把 p7 JPEG 变成屏幕像素的完整链路（谁读分区→解码到哪块内存→
> 显存物理地址→VO 图层 G0_ADDR 写什么值→HDMI 输出）仍**未坐实**。这是用户指出「最基本要求」，
> 已作为 `docs/045` 团队逆向任务的核心，本文是其地基。

## 1. format-aware：代码区 / 数据区分离（本轮实证）

对 `TMP/stock-rom-research/extracted/p01_fastboot.img`（1,048,576 B, 链接基址 `0x00C00000`）
按 4 KiB 块统计可打印 ASCII 率与函数序言密度：

| 偏移区间 | ASCII 率 | 判定 |
|---|---|---|
| `0x00000–0x7FFFF` | 28–52% | **代码区**，1313 个 ARM `push{...,lr}` 序言（首个 `0x2458`），Thumb `0xb5xx` 也有 |
| `0x80000–0x8FFFF` | 80–99% | 过渡 / 字符串 |
| `0xA0000–0xFFFFF` | **100%** | **纯数据 / 符号名池** |

→ 之前把 `0xC79E80` 一带当代码反汇编是错的：那里 `6570436f` 是 ASCII 文本。按 `docs/033 §2` 第 3 条，
**不靠字节外观推断行为**——先把区域性质定死再反汇编。

## 2. 符号名池里都有什么

`0x78000–0x83000` 共 712 个可打印串起点，显示 / HDMI / VO 相关样例：

```
0xC79D18 HDMI_Display          0xC79F4C HI_DRV_PDM_AllocReserveMem
0xC7A004 PDM_ReadLogoData      0xC7F5B4 PRODUCT_DisplayInit err
0xC7F65C boot logo show!!!     0xC8138D Can not find logo flash data
0xC81BD0 LOGO_TABLE
TX_PHY_SwingCtrl / TX_SetHDMIMode / SendAVIInfoFrame / Config4KInfoFrame（0xC79Cxx 一带）
DISP_Init / DISP_Open / DispInitDisplay / DISP_SetVirtScreen（0xC7A5xx 一带）
```

这些是**函数名 / 日志文本**，属于 stripped 后的符号名池或日志字符串。

## 3. 反查引用：结果与假阳性留痕

用 capstone 5.0.7 扫全文件 ARM + Thumb-2 的 `ldr rX,[pc,#imm]`，看目标 VA 是否落在符号名池：

| 扫描 | 结果 | 判定 |
|---|---|---|
| 全文件 ARM ldr→锚点 | 0 | — |
| 全文件 Thumb-2 ldr→锚点 | 1（`0xC79EF0 -> PDM_ReadLogoData`） | **假阳性**：`0xC79EF0` 在字符串区，是 ASCII 字节被误解码成 `ldr` |
| **仅代码区** ARM ldr→符号名池（712 个 VA） | **0** | 真负结果 |
| **仅代码区** Thumb-2 ldr→符号名池 | 25 | **全是假阳性**：25 个「命中指令」地址都在 `0xC79Cxx–0xC7FExx`（数据区），是 ASCII 误解码 |

→ **[观察] 在 p1 代码区里，找不到指向显示符号名的字面量加载**。这不是新结论（`docs/031/037` 已负），但本轮把
「代码区在哪」定死了，让负结果有明确边界，而不是扫了一堆 ASCII 得出「无引用」。

### 3.1 为什么这**不等于**「显示代码不在 p1」（必须讲清的边界）

- 函数名可能**只用于日志 / 符号表**，不通过字面量池被代码引用（按索引取用、或编译期就剥离了名字）。
- 显示代码可能以别的形式存在：BootROM 掩膜 ROM（不在任何镜像）、运行时加载的独立模块、或 p1 里未被这些
  名字标注的自包含代码段。
- 用户亲眼看到原厂开机显示 p7 图（硬事实），与「找不到显示代码」构成**矛盾**。这个矛盾必须由
  `docs/045` 的系统逆向（kallsyms / 调用图 / 代码区函数聚类）解释，不能两边挂着不管。
- **[推断·低置信]** 若这些 712 个串是完整 SDK 符号名池，而对应机器码未链接进 p1，则「通电立即显示」的
  执行者可能是 **BootROM 阶段**就从固定位置取图显示（无需函数调用名）。待实证。

## 4. 与方案的关系（回到用户的两个追问）

用户问：「一定要用阶段图吗？不能像普通程序那样填充颜色吗？」——**对，`mw.l <addr> <ARGB> <count>` 填充颜色
是最简单的方式**（hiboot 命令 `[.b,.w,.l] address value [count]` 已在三份 hiboot 实证，我们自己的
`loadfileb` 就在用 `mw.b`）。阶段图（JPEG→LOGO_TABLE→写分区→触发重画）确实更复杂，是本末倒置。

但 `mw.l` 的前提恰恰是本次没坐实的：**显存物理地址 + 刷机时 VO/HDMI 是否已初始化并持续扫描**。
`docs/046` 的方案因此建立在沙上。正确顺序是：

1. **先坐实绘制链路**（本文 + `docs/045`）：显存地址从哪来（固定常量 / `HI_DRV_PDM_AllocReserveMem`
   从 MMZ 动态分配）、`G0_ADDR` 写什么、谁读 p7 分区解码。
2. 地址若**固定可实测** → `mw.l` 填色，「只改 bootargs.bin 文本」即可，零改 p1、零图片资源、零 pstore。
3. 地址若**动态** → 才需要退化到「阶段图 + reset」或 p1 内挂一步写显存。

## 5. 已剔除的假阳性 / 误判（留痕，按 `docs/033 §2`）

1. p1 `0xC79E80` 一带当代码反汇编 → 实际是 ASCII 字符串数据。
2. Thumb-2「ldr→PDM_ReadLogoData」1 处命中 → 数据区误解码。
3. 代码区 Thumb-2「25 处 ldr→符号名池」→ 全部落在字符串区地址，误解码。
4. 原厂 p2（4 MiB）按 NUL 分割得到一堆单字符 `env keys`（'!' 'A' …）→ 是尾部填充区，不是真实 env；
   真实 env 以 `docs/027 §2.3` CRC env 结论为准。
5. p7 logo 分区里 11 处 `BM` 魔数 → 都落在那张 JPEG 数据流内部，解析不出合法 BMP 头，是压缩数据偶然字节，
   不算多图（`docs/040 §3` 教训）。p7 只有**单张** 1920×1080 JPEG @0x2000。

## 6. 交给 `docs/045` 的 4 个必答问题（用户「最基本要求」）

(a) p1 代码区确认为 `0x00000–0x7FFFF`，数据区 `0x80000+`。请在此分区基础上重做函数聚类，别把数据当代码。
(b) 显示相关机器码是否链接进 p1 代码区？给函数体 VA + 调用点；若没有，明确「代码在别处」并给最可能载体，标 [推断]/[未知]。
(c) p7 JPEG 的读取→解码→显存地址→VO `G0_ADDR`→HDMI 输出，这条链逐环坐实，坐不实标 [未知]，**不要编造地址**。
(d) 「正常开机画 logo」与「短接刷机不画」是不是两条不同执行者（U 盘根 fastboot.bin `fd5b4ac6…` ≠ 内层 `3bded87f…` ≠ 原厂 p1）。

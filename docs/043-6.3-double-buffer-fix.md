> 落地 `docs/040`（真机 fb0 实证）指出的双缓冲缺口，出一版 CI。
>

## 改动（4 个文件，均已在 `main`）

| 文件 | 改动 |
|---|---|
| `patches/kernel/hi3798mv100-hdmi-console.c` | `FB_SIZE` 8 MiB → **16 MiB（覆盖两帧）**；新增 `FB_ADDR_MARGIN`（单帧）用于地址合法性上界（否则 16 MiB 会把实测地址 `0x3f6ce000` 误判为非法）；`res.end` 加 `DDR_END` clamp 防止越界；注册成功后 `pr_info` 把 `phys/span/geometry/stride/format` 报进 pstore |
| `scripts/build-kernel.sh` | 默认 `FB_SIZE=0x1000000`，注释说明双缓冲 |
| `scripts/apply-dts-placeholders.py` | 默认 `EC6108_FB_SIZE=0x1000000`，docstring 说明 |
| `.github/workflows/build-release.yml` | `fb_size` input 默认 `0x1000000` |

**刻意不动**：fbcon/VT/`console=tty0`/`fbcon=map:0` 全部保持（`docs/042 §1` 逐条核对已齐）；
`FB_BASE` 保持空（驱动运行时从 VO 寄存器发现显存，见 `docs/041 §2`）；
驱动 `pdata.height` 仍是**单帧 1080**（simplefb/fbcon 是单帧驱动，不引入翻转回归——
这正是 153551Z、docs/024 的教训）。

## 判断修正（留痕，按 `docs/033 §2`）

初拟「把 fbcon 的 framebuffer 也改成双缓冲」是**错的**：
`docs/040` 的双缓冲是**社区 hifb 驱动**的行为，主线用 **simplefb（单帧驱动）**。
正确做法是：让 `IORESOURCE_MEM`/reserved-memory 的**保留跨度**覆盖两帧
（防止内核把第二帧分配给别人，同时 VO flip 到第二帧时地址有效），
但 fbcon 仍声明单帧 geometry。两者解耦，不互相污染。

## 三遍检查（用户偏好）

1. `bash -n build-kernel.sh`、`py_compile apply-dts-placeholders.py`、
   C 括号配平、YAML 解析、四处 `FB_SIZE` 一致性 —— 全过。
2. 完整 `git diff` 审阅：确认只动上述 4 文件、未碰 fbcon/VT/console。
3. 地址边界推演：发现 `fb_phys + 16 MiB` 在 `fb_phys≈0x3f6ce000` 时会越过
   `DDR_END=0x40000000` → 补 `res.end` clamp 防御；复查 clamp 生效、括号仍配平。

工作区两个遗留改动（`scripts/qemu-boot-test.sh` 删除、
`third_party/linux-hi3798mv100` submodule 变更）**未 stage、未提交**，原样保留。

## 出包验证要点（刷入真机后）

- HDMI 是否出现内核 fbcon 滚动文字 / 登录提示；
- 若无画面，重启进社区系统读 `/sys/fs/pstore/`（`dmesg-*` / `console-*`），
  找 `hi3798-fb: VO layer0: addr=... stride=... ireso=...` 与
  `hi3798-fb: HANDOFF phys=... span=0x1000000 ...` —— 前者是 VO 寄存器实测值，
  后者是驱动最终采用的几何；据此判断「驱动有没有找到有效显存」；
- 绿带启动标记（`docs/024`）作为「内核走到显示 initcall」的实时信号；
- 若 fbcon 之后仍无字 → 按 `docs/041` 转 P2（7.4 DRM/KMS 全量初始化）。

## 3. 软件渲染根因（新发现）

`eglinfo -B` 给出精确失败点：

```
MESA-LOADER: driver exports no extensions
  (/usr/lib/arm-linux-gnueabihf/dri/histb-vdp_dri.so: undefined symbol: __driDriverExtensions)
failed to load driver: histb-vdp
...
GBM platform:
EGL driver name: zink        ← 实际回退到软件/通用驱动
```

链上分析：

1. `histb-vdp` 是**纯显示卡**（无 render node），glamor/GBM 必须靠 Mesa kmsro shim
   `histb-vdp_dri.so` 把渲染转到 lima 的 renderD128。
2. 该 shim 由 `scripts/build-rootfs.sh:100-130` 生成：把 `lima_dri.so` 复制一份，
   把 kmsro 槽位字符串 `sun4i_drm` 原地改成 `histb_vdp`，期望导出
   `__driDriverGetExtensions_histb_vdp`。
3. 实际文件（本地 `TMP/gpu-diag/` 字节扫描）：
   `histb-vdp_dri.so` 中 `sun4i_drm`=0、`histb_vdp`=1、
   `__driDriverGetExtensions_histb_vdp`=1 —— **改名本身成功**。
4. 但 Mesa loader 对 DRM 驱动名 `histb-vdp`（**带连字符**）查找的符号是
   `__driDriverGetExtensions_histb-vdp`，而不是下划线版本；shim 里没有这个符号，
   于是报 "driver exports no extensions" 并放弃，glamor 拿到 llvmpipe 后拒绝初始化。

即：**shim 文件名的连字符/下划线处理与符号名不一致**，是 X11 仍软渲染的直接原因。

## 4. 下一步（P1/P4 衔接）

- 修 `scripts/build-rootfs.sh` 的 shim：把原地补丁目标从 `histb_vdp` 改为 `histb-vdp`
  （同样 9 字节，ELF 安全），使 `__driDriverGetExtensions_histb-vdp` 被导出；
  或在 shim 中同时保留两种符号名。
- 重跑 CI 出包、重刷，验收：`Xorg.0.log` 不再出现 `Refusing to try glamor on llvmpipe`，
  `glxinfo -B` 的 `OpenGL renderer string` = `Mali450`（`Accelerated: yes`）。
- 不修改盒子上的 DRI 文件：制品只以 CI 为准，本地只做只读诊断。
- 观察项：`CmaFree` 接近 0；`HDMI bridge misses supported HDMI version` 为非致命告警；
  warm reboot 仍未测试（继续用断电重启）。

## 5. 在线实验与最终修复（2026-11-19 续）

在测试机上做了可回退的在线实验（原 shim 与 `/etc/ec6108/gpu-mode` 均备份到盒子 `/root/`）：

1. **只把字符串 `histb_vdp` 改成 `histb-vdp`**：失败。ELF 动态符号查找依赖 `.gnu.hash`
   （bloom/buckets/chains），原地改字符串不改哈希表，`dlsym` 找不到新符号 → 仍 `failed to load driver: histb-vdp`。
2. **用脚本重建 `.gnu.hash`（两种符号名各试一次）**：
   - 连字符 `__driDriverGetExtensions_histb-vdp`：仍失败；
   - **下划线 `__driDriverGetExtensions_histb_vdp`（文件名仍是 `histb-vdp_dri.so`）：成功**。
   `eglinfo -B` 的 GBM 平台显示 `EGL driver name: histb-vdp` 且列出完整配置。
3. **真正的最后一环**：桌面服务的 `/etc/ec6108/gpu-mode` 仍在注入
   `MESA_LOADER_DRIVER_OVERRIDE=lima`，强制绕过 shim。注释掉该行（即服务注释里的"GPU 模式"）
   并 `systemctl restart ec6108-desktop` 后：

```
(II) modeset(0): glamor X acceleration enabled on Mali450
(II) modeset(0): glamor initialized
DISPLAY=:0 glxinfo -B:
  Vendor: lima (0x13b5)
  Device: Mali450
  Accelerated: yes
  OpenGL renderer string: Mali450
```

**结论**：7.4 真机已经证明可以走 Mali450 GPU 渲染；修复由两部分组成——
(a) 用 `objcopy --redefine-sym` 正确重命名 kmsro 槽位符号（自动重建 ELF 哈希表，不能字节补丁）；
(b) 取消 `MESA_LOADER_DRIVER_OVERRIDE=lima` 覆盖。当前默认包仍是软件渲染稳定态，
GPU 模式通过 `/etc/ec6108/gpu-mode` 切换。稳定性观察（是否再现硬锁死）待 3–24 小时确认。

对应代码改动：`scripts/build-rootfs.sh`（objcopy 生成 shim）、
`.github/workflows/build-release.yml`（rootfs job 装 binutils）。

## 6. 浏览器 GPU 与 4K 实验（2026-11-19 续）

### 6.1 浏览器（Chromium）

- armhf 上 `chromium 150.0.7871.100`（以及 `firefox-esr 140`）在 bookworm 源里**都有**包；
  盒子直连 Debian 源超时，通过 `ssh -R 10808:127.0.0.1:10808` 把本机代理转到盒子后装上 chromium。
- 本地 WebGL 测试页（`TMP/webgl-test.html`，未入库）在 Chromium 中显示 `WEBGL:UNAVAILABLE`。
- Chromium 日志：
  ```
  EGL Driver message (Critical) eglInitialize: Could not create a backing OpenGL context
  gl::init::CreateGLContext failed
  Exiting GPU process due to errors during initialization
  ```
  指定 `--use-angle=gl` 被拒（`Requested GL implementation ... not found in allowed
  implementations: [(gl=egl-angle,angle=default)]`）；降到 1280x720 / 640x480 仍不可用。
- 结论：**系统级 GPU 渲染（glxinfo/Mali450）可用，但 Chromium 的 ANGLE/EGL 路径无法创建 GPU
  上下文，浏览器 WebGL 不可用**。原因推测是 ANGLE 的 EGL 后端与当前 CMA/驱动组合不兼容；
  未继续深挖，记录为已知限制。

### 6.2 黑屏与 GPU 稳定性

- 中途 HDMI 无输出/背光灭，SSH 仍在线：根因是 Xorg DPMS `timeout 600` 触发 `Monitor is Off`，
  不是死机。`xset -dpms; xset s off` 后恢复，并把 DPMS/屏保关闭。
- 多次尝试 Chromium GPU 后，lima 进入 `pp0/pp1 job timeout` + `bus stop timeout` 循环，
  X 查询卡死。恢复方式：把 `/etc/ec6108/gpu-mode` 还原为软件渲染默认
  （`MESA_LOADER_DRIVER_OVERRIDE=lima`），`systemctl restart ec6108-desktop`，
  回到 `llvmpipe / Accelerated: no` 后 X 恢复正常。
- 结论：**GPU 模式适合轻量桌面展示，浏览器负载下不稳定**；默认仍应保留软件渲染。
  盒子测试机当前为软件渲染 + DPMS 关闭。

### 6.3 4K 30Hz 实验

- 显示器 EDID 提供 `3840x2160@30Hz`；Xorg 的 `xorg.conf.d/20-gpu.conf` 原本钉死 1920x1080
  （注释说 4K 单帧 ~33MB、旧 16MB CMA 下会分配失败）。
- 在软件渲染模式下执行：
  ```
  xrandr --output HDMI-1 --mode 3840x2160 --rate 30
  ```
  成功，`xrandr` 显示 `HDMI-1 connected primary 3840x2160+0+0`、当前模式 `3840x2160 30.00*`。
  `CmaFree` 降到约 2.7MB，Xorg 无真正 `(EE)` 错误，内核无新增 lima 超时，桌面服务 active。
- 结论：**4K30 模式在 KMS/Xorg 层可成功设置**（视觉确认由现场完成）；但此时是 llvmpipe
  软件渲染，4K 桌面会明显吃 CPU，且 GPU 加速路径仍不可用。
